#### DC-3 — Guards against values the types and the database schema rule out

#### DUP-2 — Storage that may refuse is guarded seven times, three different ways

- **Location**: `site/js/bundle.js:182-210` (two helper functions); `site/js/list_mode.js:75-79`, `:116-120`, `:137-143`, `:145-151` and `site/js/shopping_list.js:142-147` (five inline `try`/`catch` blocks); `site/assets/theme.js:3`, `:14` (no guard)
- **Issue**: Two helper functions and five inline blocks each implement "the browser may refuse storage", and `theme.js` goes without. The copies have drifted in a way that matters. The helpers take the storage object as an argument, so it is read at the call site, before the helper's `try` begins; the inline blocks read it inside theirs:

  ```js
  // site/js/bundle.js:31
  const remembered = readStorage(sessionStorage, BUNDLE_URL_STORAGE_KEY);

  // site/js/list_mode.js:138-142
  try {
      return (sessionStorage.getItem(SELECTION_STORAGE_KEY) ?? "").split(",").filter(Boolean);
  } catch {
      return [];
  }
  ```

  When a browser blocks site data, it is the read of `sessionStorage` itself that throws. NV-1 has the consequence.
- **Proposed change**: Move the helpers to their own module, have them take the storage's name (`"sessionStorage"`, `"localStorage"`) and look it up inside the `try`, and replace the five inline blocks with calls. For `list_mode.js` and `shopping_list.js` this preserves behavior as long as the helper stores an empty string as an empty string; the current `writeStorage` removes the key instead (`bundle.js:202-203`), which reads back the same (`list_mode.js:139`) but leaves different storage contents. Switching `bundle.js` to the same helper is not a quality change; it is the fix for NV-1.
- **Confidence it's safe**: **Medium**. Trial: with one such module in a throwaway clone, the three checks passed and markup, address bar and session storage were identical to the baseline in 160 page states.
- **Verification**: the three checks, then NV-1's experiment.
